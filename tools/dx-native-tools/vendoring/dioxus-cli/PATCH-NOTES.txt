================================================================================
PATCH NOTES: dioxus-cli (the `dx` build tool)
================================================================================

tools/dx-native-tools/sources/dioxus-cli is the dioxus-cli crate exactly as
published on crates.io (the archive beside this file, whose checksum is in the
.sha256 file) with the numbered patches in this folder applied in order.
Nothing else may differ: `LibraryChecker patches` rebuilds the source from the
archive and the patches and compares it with that folder byte for byte.

Every patch was written against the dioxus-cli version named by the archive
beside this file. When the tool is upgraded, each patch is re-applied to the
new source (see UPGRADE-README.txt) and this file is brought up to date.

Each changed place in the source carries a comment that starts "CodeBrix
change:" and points at this file, so the changes can be found with a search.

The patches, in the order they apply:
  0001-image-crate-encoders.patch           image encoders without imagequant
                                            and mozjpeg
  0002-libgit2-sys-stand-in.patch           libgit2-sys -> the declarations-only
                                            stand-in (prebuilt libgit2)
  0003-build-without-esbuild.patch          web builds without esbuild
  0004-regenerated-cargo-lock.patch         the lock file for 0001 + 0002
  0005-no-prebuilt-openssl.patch            no prebuilt OpenSSL archive
  0006-release-build-without-wasm-opt.patch DX_SKIP_WASM_OPT: an unshrunk
                                            release build on request
  0007-wasm-split-cli-call-graph.patch      wasm-split-cli -> the patched copy
                                            (the splitter's call graph, and
                                            its reproducible output)
  0008-tailwind-output-in-assets-generated.patch
                                            Tailwind's default output is
                                            assets/generated/tailwind.css
  0009-unsplit-build-split-loader.patch     a build or `dx serve` WITHOUT
                                            bundle splitting of an application
                                            with split points gets a stand-in
                                            __wasm_split.js
  0010-site-root-addresses-without-dot.patch
                                            "/assets/..." instead of
                                            "/./assets/..." for an application
                                            at the site root
  0011-split-shared-chunk-options.patch     DX_WASM_SPLIT_CHUNK_THRESHOLD and
                                            DX_WASM_SPLIT_CHUNK_LIMIT: several

linux-arm64, osx-arm64, osx-x64 and win-x64 (dx.exe) carry all thirteen
(adopted 2026-11-27). The FrontendBuilder refuses a split build with a dx
without 0011.


0001-image-crate-encoders.patch
-------------------------------
What:   src/opt/image.rs - compress_png and compress_jpg are rewritten to use
        the `image` crate's own PNG and JPEG encoders. Cargo.toml - the
        `imagequant` and `mozjpeg` dependencies are removed.
Why:    `imagequant` is licensed GPL-3.0-or-later and `mozjpeg` /
        `mozjpeg-sys` under the IJG license, neither of which this
        repository accepts. Both were used only to make image assets smaller.
Effect: image assets processed by `dx` are larger: PNG files keep full
        colour instead of being reduced to a 256-colour palette, and JPEG
        files are encoded at quality 85 by a simpler encoder. Nothing else
        changes. `nasm` is no longer needed to build the tool.
Drop when: upstream stops depending on `imagequant` and `mozjpeg`, or puts
        them behind a cargo feature that can be left off.


0002-libgit2-sys-stand-in.patch
-------------------------------
What:   Cargo.toml - a [patch.crates-io.libgit2-sys] section that replaces the
        crates.io crate libgit2-sys with the repository's own crate in
        tools/dx-native-tools/sources/codebrix-libgit2-sys (path
        "../codebrix-libgit2-sys"). Nothing else: `dx new`, `dx init` and the
        libgit2-based `dx components` are upstream's, unchanged, and so are
        the `git2` and `cargo-generate` dependencies.
Why:    git2 (which dx uses directly, and through cargo-generate and
        auth-git2) builds on libgit2-sys, which carries libgit2's C source
        (GPL-2.0 with a linking exception) and compiles it. This repository
        never carries libgit2's source. The stand-in has the same crate name,
        version (0.18.3), features and public Rust API as libgit2-sys
        0.18.3+1.9.2 but no C code: it declares libgit2's functions (its lib.rs
        is upstream's, with three marked changes) and links the PREBUILT
        libgit2 1.9.7 of the published package CodeBrix.LibGit2.MitLicenseForever
        as a shared library (see its README.txt). Because of the substitution,
        cargo vendor never takes the crates.io libgit2-sys, nor libssh2-sys or
        libz-sys.
Effect: every dx command is there again. dx LINKS libgit2 and does not start
        without it (tools/dx-native-tools/README.txt, "dx NEEDS libgit2 TO
        START"). The build needs CODEBRIX_LIBGIT2_LIB_DIR naming the folder
        with the library to link (the build scripts set it). On Linux the
        build also needs the OpenSSL development headers, for a reason that
        is not this patch's: cargo-generate turns on git2's `https` feature,
        which makes git2 depend on openssl-sys on Linux; git2 never calls it,
        so nothing from OpenSSL is linked into dx, but openssl-sys's build
        script reads the headers (linux/pins.env, OPENSSL_DEVEL_VERSION).
        `dx components add` downloads third-party source into a project's own
        src folder, outside the vendored snapshots and the license gate.
History: until 2026-11-19 patch 0002 was "host-git-no-project-templates": it
        deleted `dx new` and `dx init`, removed the cargo-generate and git2
        dependencies and made `dx components` run the `git` program. The
        repository owner had that undone, all of dx's functionality put back,
        and this patch put in its place.
Drop when: never while this repository may not carry libgit2's source; on an
        upgrade, re-check that the stand-in's version still matches the
        libgit2-sys that dx's git2 asks for.


0003-build-without-esbuild.patch
--------------------------------
What:   - src/build/web.rs - a missing `esbuild` no longer stops a web build.
        - src/opt/js.rs - when a JavaScript module is copied without esbuild,
          the `snippets` folder that wasm-bindgen writes beside it is copied
          beside the output file; and so is `__wasm_split.js`, the loader a
          build with bundle splitting (`--wasm-split`) writes beside the glue
          file, under a name that carries a hash of its content
          (`__wasm_split-dxh<hash>.js`), with the glue file's `import ... from`
          lines rewritten to that name (and nothing else: the glue file hands
          the loader to the WebAssembly module under the ORIGINAL name, which
          is the name that module imports).
Why:    upstream requires the `esbuild` program for every web build and, when
        it is absent, downloads it from the npm registry. This repository
        installs no JavaScript tooling and its `dx` is built with downloads
        switched off. esbuild's job here is to fold the small JavaScript
        files that Dioxus and wasm-bindgen generate into one file and minify
        it; the application works the same without that.
Effect: the generated JavaScript is served as it was generated: one glue
        file plus a few module files under assets/snippets, not minified.
        `dx` prints "esbuild binary path not set. Copying JS without
        processing." on every build; that is expected. If an `esbuild`
        program IS on PATH, `dx` uses it as upstream does.
        BUNDLE SPLITTING: upstream leaves the loader to esbuild and removes
        the folder it was written to, so without this part of the patch a
        split release build ships a glue file that imports a file that is not
        there, and the page never starts. The loader lists the addresses of
        the split modules, which change with every build; the hash in its
        name keeps a browser from reusing an older build's copy. The loader
        has no imports of its own.
Drop when: upstream makes esbuild optional.
Status: kept by the repository owner's decision. The alternative, installing
        an `esbuild` program, was considered and declined.


0004-regenerated-cargo-lock.patch
---------------------------------
What:   - Cargo.lock - regenerated by cargo after the Cargo.toml edits of
          patches 0001 and 0002, starting from upstream's own Cargo.lock.
          Packages that nothing depends on any more are removed (imagequant,
          mozjpeg and their trees, and libgit2-sys 0.18.3+1.9.2 with
          libssh2-sys and libz-sys); the stand-in libgit2-sys 0.18.3+1.9.7 is
          added as a local package; no other package is added and none
          changes version.
        - .gitignore - the `Cargo.lock` line is removed.
Why:    the lock file must match the manifest, and the upstream .gitignore
        would make git ignore the lock file, so a clone of this repository
        could not build the tool with `--locked`.
Effect: none on behaviour.
Regenerate, do not re-apply: on an upgrade this patch is not carried
        forward. After the other patches are applied to the new source, run
        `cargo metadata` in the dioxus-cli source once with network access (or
        `cargo vendor`, which resolves against crates.io) so cargo prunes
        the lock file. cargo keeps the locked crates.io libgit2-sys and
        reports the patch as unused until it is told once to switch:
        `cargo update -p libgit2-sys@<the locked version>` (it then removes
        that crate with libssh2-sys and libz-sys and changes nothing else).
        Then write a new patch from the result.


0005-no-prebuilt-openssl.patch
------------------------------
What:   - assets/android/prebuilt/openssl-1.1.1q-beta-1.tar.gz is deleted (a
          `delete-file` line; see PATCHES in the root MAINTAINER-README.txt).
        - src/build/android.rs - `openssl_prebuilt_aar` is removed and
          `unpack_prebuilt_openssl` no longer unpacks anything.
Why:    the archive is a prebuilt binary build of OpenSSL 1.1.1 for Android
        (under the old OpenSSL license) that upstream compiles into `dx` and
        unpacks for Android builds. This repository carries source it can
        account for, not prebuilt binaries, and builds nothing for Android.
        The file cannot simply be removed: the source embeds it at compile
        time, so the tool would not build.
Effect: none on a web build. An Android build made with this `dx` gets no
        OpenSSL from the tool; an application that links OpenSSL must name
        its own with OPENSSL_LIB_DIR and OPENSSL_INCLUDE_DIR. The README.md
        in assets/android/prebuilt is upstream's and is left as it is; it
        describes the archive that is no longer there.
Drop when: upstream stops shipping the archive inside the crate.
Numbered after 0004 because it was added later; it does not touch Cargo.toml
        or the lock file, so on an upgrade it is re-applied with 0001 to 0003,
        before 0004 is regenerated.


0006-release-build-without-wasm-opt.patch
-----------------------------------------
What:   src/build/web.rs - where a web build runs wasm-opt on the main
        WebAssembly module, the environment variable DX_SKIP_WASM_OPT is read:
        when it is set to anything but an empty value, "0" or "false" (any
        case), the step is skipped and dx prints one line, "Skipping wasm-opt
        at the caller's request (DX_SKIP_WASM_OPT is set): the WebAssembly is
        not shrunk".
Why:    upstream runs wasm-opt on EVERY release web build and has no way to
        skip it; with no wasm-opt available a release build fails ("Missing
        wasm-opt"). The platform's rule is that shrinking is on for release
        builds and off for debug builds, with one documented override either
        way. Shrinking a debug build needs nothing from dx (the
        FrontendBuilder library runs wasm-opt after dx); the other direction -
        an unshrunk release build - needs this. An environment variable rather
        than a command-line flag, so nothing in dx's argument parsing or its
        configuration schema changes.
Effect: unset (or "0" / "false"): exactly upstream's behaviour. Set: a
        release build neither looks for nor runs wasm-opt for the main
        module, so it succeeds with no wasm-opt on the machine, and the
        .wasm is the larger file wasm-bindgen wrote. A debug build is
        unaffected either way (dx never shrinks one). BUNDLE SPLITTING
        (`--wasm-split`) keeps its own behaviour: it needs wasm-opt for the
        split modules, which dx shrinks as it writes them, and for the main
        module, so with bundle splitting the variable is IGNORED and wasm-opt
        runs as upstream does.
Drop when: upstream offers a way to skip wasm-opt for a release build.
Does not touch Cargo.toml or the lock file; on an upgrade it is re-applied
        with 0001 to 0003 and 0005, before 0004 is regenerated.


0007-wasm-split-cli-call-graph.patch
------------------------------------
What:   - Cargo.toml - a [patch.crates-io.wasm-split-cli] section that replaces
          the crates.io crate wasm-split-cli 0.7.10 (the WebAssembly bundle
          splitter dx runs for `dx build --wasm-split`) with the repository's
          patched copy of the same release in
          tools/dx-native-tools/sources/wasm-split-cli (path
          "../wasm-split-cli"). That copy is the crates.io archive in
          tools/dx-native-tools/vendoring/wasm-split-cli plus the patches
          recorded there, checked by `LibraryChecker patches` like this tool.
        - Cargo.lock - the wasm-split-cli entry loses its crates.io source and
          checksum (cargo's own result of the substitution; nothing else
          changes). Because of the substitution, `cargo vendor` does not take
          the crates.io wasm-split-cli, so it was removed from sources/vendor.
Why:    `dx build --wasm-split` panicked ("assertion failed:
        !self.dead.contains(&id)") when a split route used a function that a
        closure shim of the main module also calls - for example an input
        field that reads its value, on a split page only. The splitter's call
        graph is fixed in the patched copy; the bug, the evidence, the two
        changes and upstream's status are in
        tools/dx-native-tools/vendoring/wasm-split-cli/PATCH-NOTES.txt. The
        same copy also carries a later, separate fix (its patch 0003, added
        2026-11-19): the splitter wrote a split module's element and data
        segments in the random order of a HashMap / HashSet, so the same
        source gave other split modules, and other content-hashed file names,
        on every build. This patch (0007) did not change for it.
Effect: a split build no longer panics there. The closure shims and what they
        call stay in the main module; split routes still get their own code.
        With the splitter's patch 0003, a split build gives the same files,
        names and bytes from the same source every time. Builds without
        --wasm-split do not run the splitter and are unaffected.
Drop when: the splitter's patches can be dropped (see that file).
Status: approved by the repository owner 2026-11-19 ("diagnose and fix").
On an upgrade: the Cargo.toml part is re-applied with 0001 to 0003, 0005 and
        0006, before 0004 is regenerated, and 0004's regeneration then
        includes the lock change; the [patch] must name the wasm-split-cli
        release the new dx asks for.

0008-tailwind-output-in-assets-generated.patch
---------------------------------------------
What:   src/tailwind.rs, TailwindCli::run - when Dioxus.toml sets no
        `tailwind_output`, the stylesheet Tailwind writes is
        <package folder>/assets/generated/tailwind.css (upstream:
        <package folder>/assets/tailwind.css). The folder is created when it
        is missing, as upstream already did for assets/. Nothing else: the
        input default (<package folder>/tailwind.css), the v3 / v4 detection
        and the `tailwind_input` / `tailwind_output` settings are upstream's.
Why:    the platform's generated stylesheet has one fixed place,
        <frontend>/assets/generated/tailwind.css, so that build output does
        not sit among the developer's own assets: the FrontendBuilder library
        owns assets/generated (it writes the folder's .gitignore and makes the
        stylesheet there when it is missing) and refuses a Dioxus.toml that
        sets either Tailwind path. dx must write to the same file in every
        build and in `dx serve`, or the application's asset!() reference and
        the file dx keeps up to date would be two different files.
Effect: dx (build and serve) writes Tailwind's output to
        assets/generated/tailwind.css. dx does not write a .gitignore; the
        library does. A RELATIVE `tailwind_output` (or `tailwind_input`) is,
        as upstream, passed to tailwindcss unchanged and resolved by
        tailwindcss against the package folder (dx starts it there); dx's own
        "create the parent folder" step for a relative setting resolves it
        against dx's working directory instead, which is the same folder only
        when dx is started in the package folder (the FrontendBuilder library
        does start it there). Projects outside the platform that relied on
        the old default must set `tailwind_output = "assets/tailwind.css"`.
Drop when: never while the platform's generated stylesheet lives in
        assets/generated; on an upgrade, re-apply it with 0001 to 0003 and
        0005 to 0007 (it does not touch Cargo.toml or the lock file).
Status: decided by the repository owner, 2026-11-24 (the frontend's fixed
        folder layout).
        In the adopted programs (BUILD-PROVENANCE.txt): linux-x64 and
        linux-arm64 since 2026-11-24; win-x64, osx-arm64 and osx-x64 since
        their dx rebuilds of 2026-11-24.

0009-unsplit-build-split-loader.patch
-------------------------------------
What:   src/build/web.rs - bundle_web, for a web build WITHOUT bundle
        splitting (no `--wasm-split`; `dx serve` never splits): after
        wasm-bindgen, the new function write_unsplit_split_loader reads the
        imports of the module wasm-bindgen wrote. When it imports from
        "./__wasm_split.js" (the module name under which the `wasm_split`
        macros - `wasm_split::lazy_loader!`, `#[wasm_split]` and dioxus's
        `#[component(lazy)]` - import a split point's loader on wasm32), dx
        writes `__wasm_split.js` beside the glue file, a stand-in loader:
          - every `__wasm_split_load_<module>_<hash>_<name>(callback, data)`
            calls the callback through the module's function table with
            (data, true), in a microtask (the real loader calls it after its
            fetch): "this piece is already loaded";
          - every `__wasm_split_00___<module>___00_import_<hash>_<name>(...)`
            (a piece's entry point) calls the function the main module
            exports as `__wasm_split_00___<module>___00_export_<hash>_<name>`
            - the same code, which an unsplit build keeps in the main module
            and exports (the macros mark it #[no_mangle]);
          - any other name imported from that module gets a function that
            throws an error naming it (none exists in dioxus 0.7.10).
        The callback needs the function table, which an unsplit module does
        not export (only a split main module and a hot-patch build do). When
        table 0 is not exported, dx adds ONE export to the module wasm-bindgen
        wrote: table 0 under the name `__indirect_function_table` (the name a
        split main module and a hot-patch build use). Only the export section
        is rewritten; every other section is copied byte for byte, so DWARF
        offsets into the code section stay valid. A module that imports
        nothing from "./__wasm_split.js" is not touched and gets no file.
        The stand-in reaches the module's exports through
        globalThis.__wasm_split_main_initSync, which dx's glue shim already
        sets for the real loader, so the glue file is unchanged.
Why:    with the `wasm-split` feature of dioxus on, the main module ALWAYS
        imports "./__wasm_split.js" on wasm32, and upstream writes that file
        only for a split build. Every unsplit build and every `dx serve` of
        such an application gave a page that never started (the module
        script's import fails: 404 from a backend, or dx serve's fallback
        index.html with no JavaScript content type), with no error from the
        build. That left a split application with no development loop and no
        working unsplit build.
Effect: an application with split points works without splitting: built
        unsplit (debug or release) or served, all of its code is in the one
        main module and the split points resolve at once. The main module
        carries one more export (the function table). A RELEASE build ships
        the stand-in under a content-hashed name
        (`__wasm_split-dxh<hash>.js`, through patch 0003's copy step, which
        handles it exactly as it handles the real loader); a DEBUG build and
        `dx serve` serve it as wasm/__wasm_split.js beside the glue file.
        Builds WITH --wasm-split are unchanged (the splitter writes the real
        loader), and so are applications without split points.
Upstream: upstream has the same defect (the macros import the loader
        unconditionally; dx writes it only in the --wasm-split branch of
        bundle_web). No upstream issue or fix was looked up for this patch.
How checked: the ApplicationSplitter sample's sales application (a scratch
        copy, the published packages, a dx built from this source) built
        WITHOUT splitting, release and debug, and served with `dx serve`:
        each page loads (deep links included), the formatting self-check
        and the diagnostics tables report 0 failures, and the three
        hand-split parts work in headless Chrome - the lazy component
        (customers page, "Show insights"), the `#[wasm_split]` function
        (reports page, "Run the forecast") and the `lazy_loader!` panel
        (orders page, "Details") - with no console error and no request for
        a piece. With the published dx the same build stays blank
        (`__wasm_split.js`: 404).
Drop when: upstream writes a loader (or no import) for unsplit builds.
Does not touch Cargo.toml or the lock file (wasmparser and serde_json are
        dx dependencies already); on an upgrade it is re-applied with 0001 to
        0003 and 0005 to 0008, before 0004 is regenerated.
Status: made under the repository owner's GO of 2026-11-24 (S2 / B1).
        In the adopted programs (BUILD-PROVENANCE.txt): linux-x64 and
        linux-arm64 since 2026-11-24; win-x64, osx-arm64 and osx-x64 since
        their dx rebuilds of 2026-11-24.


0010-site-root-addresses-without-dot.patch
------------------------------------------
What:   src/build/web.rs - the absolute addresses dx writes for an
        application's own files start "/assets/..." or "/wasm/..." for an
        application at the site root (no base path) and "/<base path>/..."
        otherwise. Upstream builds them from base_path_or_default(), which is
        "." without a base path, and writes "/./assets/...". Changed, through
        one new helper (base_path_prefix): the script tag dx adds to
        index.html, the glue shim's .wasm address, the split loader's
        addresses of the split modules and chunks, and every
        "/{base_path}/" in index.html (the form dx's own head resources -
        stylesheets, preloads, scripts - and a hand-written index.html use).
        A {base_path} written in any other way is replaced as upstream does.
Why:    "/./assets/..." works (a browser removes the "./" when it resolves
        the address) but is not the address of the file: it shows in the
        page source, the network log and any tool that reads index.html.
Effect: the root application's index.html links "/assets/<script>" (release)
        or "/wasm/<script>" (debug, serve) and its glue file loads
        "/assets/<module>.wasm". Applications with a base path are
        unchanged ("/sales/assets/...").
How checked: the ApplicationSplitter sample's root application (home) built
        release and debug with a dx from this source: index.html and the glue
        file carry "/assets/..." and "/wasm/..." addresses, and the page loads
        in headless Chrome.
Drop when: upstream stops writing "/./".
Does not touch Cargo.toml or the lock file; on an upgrade it is re-applied
        after 0009 (both change src/build/web.rs).
Status: made under the repository owner's GO of 2026-11-24.
        In the adopted programs (BUILD-PROVENANCE.txt): linux-x64 and
        linux-arm64 since 2026-11-24; win-x64, osx-arm64 and osx-x64 since
        their dx rebuilds of 2026-11-24.


0011-split-shared-chunk-options.patch
-------------------------------------
What:   src/build/web.rs - bundle_web, in a build WITH bundle splitting
        (`--wasm-split`), reads two environment variables and passes them to
        the splitter (wasm-split-cli's Splitter::new_with_options, splitter
        patch 0007) instead of calling Splitter::new:
          DX_WASM_SPLIT_CHUNK_THRESHOLD  the size, in bytes of code and data
                                         before optimisation, from which a
                                         group of shared code gets a chunk of
                                         its own (SplitOptions::chunk_threshold)
          DX_WASM_SPLIT_CHUNK_LIMIT      the most shared chunks, the common
                                         chunk included (chunk_limit; unset:
                                         the splitter's default, 16)
        Unset or empty: the splitter's default, ONE chunk for all shared code,
        exactly as before. Both are checked at the START of a split web build
        (verify_web_tooling, before wasm-bindgen is looked for and before
        cargo runs): a value that is not a positive whole number (digits only,
        at least 1) stops the build there with a message of its own:
          Bundle splitting cannot start: the environment variable
          DX_WASM_SPLIT_CHUNK_THRESHOLD (the size in bytes from which shared
          code gets a chunk of its own; unset: one chunk for all shared code)
          must be a positive whole number - digits only, at least 1 - or
          unset; it is "abc". Nothing was built.
        (the same for DX_WASM_SPLIT_CHUNK_LIMIT). Unit tests (mod
        split_chunk_option_tests): unset and empty, accepted values, refused
        values of each variable, the line below. After splitting, dx prints
        one line at INFO level:
          Bundle splitting: 3 shared chunks (threshold 16384 bytes, limit 16)
          Bundle splitting: 1 shared chunk (no threshold: one chunk for all shared code)
        (the number counts every chunk file written, the common chunk
        included, which is written even when empty). Builds without
        splitting read neither variable and print no such line.
Why:    the platform's build library (FrontendBuilder) sets both from
        PlatformFrontendOptions.SharedChunkThreshold / SharedChunkLimit for
        every build, so that shared code only some pieces use is fetched only
        by them (splitter patch 0007 has the reasons and the measurements).
        Environment variables, as for DX_SKIP_WASM_OPT (0006), so nothing in
        dx's arguments or configuration schema changes. The line lets the
        library tell this dx from one that ignores the variables: it fails a
        split build whose dx printed none.
Effect: a split build gets several shared chunks when asked; dx writes one
        chunk_<n>_split-dxh<hash>.wasm per chunk and lists each module's chunks in the
        loader (in order; the splitter's 0007). Unset: unchanged output, one
        more log line. Unsplit builds and `dx serve`: unchanged.
Drop when: with splitter patch 0007.
Does not touch Cargo.toml or the lock file; on an upgrade it is re-applied
        after 0010 (all of 0009 to 0013 change src/build/web.rs).
Status: made under the repository owner's GO of 2026-11-27.


0012-split-release-glue-without-debug.patch
-------------------------------------------
What:   src/build/web.rs - bundle_web passes wasm-bindgen's `--debug` only when
        the build asks for debug output for its own sake (the configuration's
        wasm_opt.debug, --debug-symbols, a debug build, a hot-patch build).
        Upstream passed it with `--keep-debug` whenever the build was split
        (`keep_debug` includes `self.wasm_split`). `--keep-debug` is still
        passed: the splitter reads the sections it keeps.
Why:    `--debug` only changes the generated JavaScript - it wraps every
        browser call in error logging and adds argument checks - and a split
        release build shipped that glue. Measured on three split applications
        with wasm-bindgen 0.2.130: the module wasm-bindgen writes is byte for
        byte the same with and without `--debug` (so the split output is
        too), and the glue JavaScript is 16 to 18 per cent smaller without it
        (about 0.5 to 0.7 KB Brotli); the ApplicationSplitter sample's sales
        application worked in headless Chrome with the smaller glue (every
        page, the hand-split parts, no console error).
Effect: a RELEASE build with bundle splitting: the glue .js (and so its
        hashed name and index.html) changes, without the debug checks; every
        .wasm is unchanged. Debug builds, unsplit builds and `dx serve`:
        unchanged.
Drop when: upstream stops passing --debug for split release builds.
Does not touch Cargo.toml or the lock file; re-applied after 0011.
Status: made under the repository owner's GO of 2026-11-27.


0013-split-module-file-names.patch
----------------------------------
What:   src/build/web.rs - bundle_web names a split module's file
        `module_<n>_<name part>.wasm` with the name part of
        split_module_file_stem (new) instead of the name of the function the
        split point calls (upstream: `module_<n>_<function>.wasm`). The
        splitter gives every split module the name of its PIECE (the module
        name of its import, `__wasm_split_00___<piece>___00_import_...`) and
        of its function:
          lazy_loader!(extern "NAME" fn f(..))   piece NAME, function f
          #[wasm_split(NAME)] async fn f(..)     piece NAME, function f
          #[component(lazy)] fn Name(..)         piece "lazy" (always exactly
                                                 that: dioxus-core-macro writes
                                                 lazy_loader!(extern "lazy" fn
                                                 Lazy<Name>(..))), function
                                                 Lazy<Name> ("Lazy" + the
                                                 component function's name)
          a route (the router's macro)           piece module<Route><hash>,
                                                 function route<Route><hash>
                                                 (the same 32 hexadecimal
                                                 digits after the same name)
        The rule:
          - a ROUTE - the piece name is "module" + X and the function name
            "route" + X, X ending in 32 lowercase hexadecimal digits: the
            function's name, `route<Route><hash>`, as before;
          - a LAZY COMPONENT - the piece name is "lazy": `lazy_<function>`,
            ALWAYS, also when it is the only one, so that adding a second
            lazy component renames no file (a lazy_loader! piece a developer
            names "lazy" is treated the same);
          - any other piece name that several split points share:
            `<piece>_<function>`;
          - otherwise the piece name (an empty one: the function's name).
        Examples: lazy_loader!(extern "details" fn panel(..)) ->
        module_4_details.wasm; a lazy component Insights ->
        module_1_lazy_LazyInsights.wasm, alone or beside others (Chart ->
        module_2_lazy_LazyChart.wasm); two lazy_loader! pieces both named
        "reports" calling monthly and yearly -> module_5_reports_monthly.wasm
        and module_6_reports_yearly.wasm; the route Orders ->
        module_7_routeOrders<hash>.wasm, as before. Both names are made of
        ASCII letters, digits and `_` (the wasm_split macros make
        `#[no_mangle]` items of them, which must be ASCII), so the name is a
        safe file and address; the `module_<n>_` before it keeps every file
        apart. The loader's export names (`__wasm_split_load_<piece>_<hash>_
        <function>`), which the main module imports, are unchanged; dx then
        adds its content hash to the file name as before (`-dxh<hash>`).
        Unit tests (mod split_module_file_name_tests): a named piece, a lazy
        component alone and beside others, a shared piece name, a route, a
        look-alike that is no route, an empty piece name.
        The lazy-component rule was added on review (2026-11-27) and awaits
        the repository owner's confirmation; without it (the first version)
        a lone lazy component's file was module_<n>_lazy. To go back, in
        split_module_file_stem change `} else if shared || piece ==
        LAZY_COMPONENT_PIECE {` to `} else if shared {`, remove the constant
        LAZY_COMPONENT_PIECE and the test
        a_lazy_component_always_carries_its_function_name (and its line in
        the doc comment), and write this patch again.
Why:    the platform's guide calls a piece by the name the developer gives
        it (`extern "details"`, `#[wasm_split(forecast)]`); the file of a
        lazy_loader! piece carried the function's name instead, so the files
        did not tell which piece is which.
Effect: the files of lazy_loader!, #[wasm_split] and lazy-component pieces
        get new names (a returning visitor downloads them once); route
        pieces and the shared chunks keep theirs. Nothing else depends on
        the names: the loader lists the addresses dx gives it, and the
        platform's backend serves and caches any `-dxh` name.
Drop when: upstream names split modules after their piece.
Does not touch Cargo.toml or the lock file; re-applied after 0012.
Status: made under the repository owner's GO of 2026-11-27.


BUILD SWITCHES (not a patch)
----------------------------
The native build (tools/dx-native-tools, DX_FEATURES in linux/pins.env)
builds the tool with the cargo features `no-downloads` and
`disable-telemetry`, both of which upstream provides:
  - no-downloads: `dx` never downloads a tool. It uses the `wasm-bindgen`,
    `tailwindcss` and `wasm-opt` it finds on PATH (the FrontendBuilder library
    puts the packaged Tailwind, wasm-opt and wasm-bindgen first there).
  - disable-telemetry: upstream `dx` uploads usage data. With this feature
    its "is telemetry disabled" check always answers yes, so no reporter is
    enrolled, and every upload path needs a reporter and stops without one.
    Nothing is written to the tool's statistics folder either.
