PATCH NOTES: wasm-split-cli (the WebAssembly bundle splitter inside `dx`)
================================================================================

tools/dx-native-tools/sources/wasm-split-cli is the wasm-split-cli crate exactly
as published on crates.io (the archive beside this file, whose checksum is in
the .sha256 file) with the numbered patches in this folder applied in order.
Nothing else may differ: `LibraryChecker patches` rebuilds the source from the
archive and the patches and compares it with that folder byte for byte.

wasm-split-cli is a library crate of the Dioxus project
(https://github.com/DioxusLabs/dioxus, packages/wasm-split/wasm-split-cli),
"MIT OR Apache-2.0", used under Apache-2.0 like dx itself. It is not a separate
program here: dx links it and runs it for `dx build --wasm-split`. dx's
Cargo.toml substitutes this patched copy for the crates.io crate
(tools/dx-native-tools/vendoring/dioxus-cli, patch 0007), so `cargo vendor`
does not take the crates.io copy and it is not in sources/vendor; the archive
here is the pristine crate.

Each changed place in the source carries a comment that starts "CodeBrix
change:" and points at this file.

The patches, in the order they apply:
  0001-recovered-edges-into-call-graph.patch       the edges the splitter
                                                   meant to give `main` reach
                                                   its call graph
  0002-no-edges-from-type-index-relocations.patch  a call_indirect's type
                                                   index is not read as a
                                                   symbol
  0003-deterministic-split-module-sections.patch   the same input gives the
                                                   same split modules, byte
                                                   for byte
  0004-keep-main-data-inside-split-symbols.patch   the main module keeps its
                                                   constants that the linker
                                                   stored inside a split
                                                   module's constant

All four patches change src/lib.rs only. 0001 and 0002 belong together: 0001
is the fix of the panic, and 0002 keeps 0001 from pinning most of a split
route's code into the main module (see the Effect of each). 0003 is a separate
fix (reproducible output) and has its own section below, and so is 0004 (the
main module's data).

Status of 0001 and 0002: approved by the repository owner 2026-11-19
("diagnose and fix"). Status of 0003: made under the repository owner's GO of
2026-11-19 for the investigation of the changing file names of a split
application and "fixing whatever you need to fix". Status of 0004: made under
the repository owner's GO of 2026-11-23 ("GO on the fix").


THE BUG 0001 AND 0002 FIX
-------------------------
`dx build --platform web --release --wasm-split` panicked right after "Emitting
main bundle split module":

    assertion failed: !self.dead.contains(&id)
    (walrus-0.23.3/src/module/functions/mod.rs, from walrus::passes::gc::run
    in Splitter::emit_main_module)

A small application reproduces it deterministically: two split routes, and an
input field whose handler reads the field's value (`oninput: move |e|
typed.set(e.value())`) on ONE of them and nowhere in the main module. Upstream
issue DioxusLabs/dioxus#4769 reports the same panic (open).

How the splitter works: it builds a call graph of the program from the
relocations rustc leaves in the module (`--emit-relocs`), pairs the original
module's functions with the module wasm-bindgen wrote, computes what the main
module reaches and what each split route reaches, and deletes from the main
module every function that only split routes reach.

What went wrong, proved by dumping the splitter's sets for that application:

  - wasm-bindgen replaces its "describe" functions with generated glue. A
    describe function is the only code that names the `invoke` shim of a
    closure type (the function JavaScript calls through the function table
    when it calls a Rust closure). The splitter knows this: build_call_graph
    collects everything those vanished functions referenced ("recovered
    children") and every function only wasm-bindgen made, and attaches them
    to `main`. But it attached them in a LOCAL map, `new_call_graph`, that is
    never read again. So those shims were reachable from nothing.
  - They stay in the main module anyway: they sit in the function table,
    which is exported. Two of them (the shims of the closure types js-sys's
    Array::flatMap takes) call alloc::vec::Vec<JsValue>::into_boxed_slice.
    The form code of the split route also calls that function, and nothing
    else in the graph does, so it counted as "only a split route reaches it"
    and was deleted from the main module while the shims still called it.
    walrus's garbage collector then walked the dangling call and panicked.
  - With a field in the main module too (the workaround the
    ApplicationSplitter sample used), the main module itself reaches the
    form code, so nothing the shims call is deleted. Whether a build panics
    therefore depended on which functions a split route happens to share
    with such a shim.

Upstream status (checked 2026-11-19): the code is unchanged on upstream's main
branch, and there is no release after 0.7.10 except 0.8.0 pre-releases, which
this repository does not take. No fix is merged.


0001-recovered-edges-into-call-graph.patch
------------------------------------------
What:   src/lib.rs, build_call_graph - the edges from `main` to the recovered
        children and to the functions only wasm-bindgen made are written into
        `self.call_graph`, the graph the main module's reachability is
        computed from, instead of into the discarded local map
        `new_call_graph`, which is removed (with the empty entries it was
        given). This is exactly the change of upstream's open pull request
        DioxusLabs/dioxus#5795 (its one commit,
        3f6e5a950dfd29cb60ae2d1b76d22c0bd7cd1301), with our own comments.
Why:    it makes the splitter do what its own comments say it does. Without
        it, a function reached only through such a shim can be deleted from
        the main module while still called, and the build panics (above).
Effect: the closure shims, the functions only wasm-bindgen made, and what
        they call are kept in the main module, which they never left; a split
        module that uses one of those functions now imports it from the main
        module instead of deleting it there. The panic is gone. ON ITS OWN
        this patch pins far too much into the main module, because of the
        defect 0002 fixes: in the small reproduction no function at all was
        left in the split routes.
Drop when: upstream merges #5795 or an equivalent fix and the repository
        takes a stable release that has it.


0002-no-edges-from-type-index-relocations.patch
-----------------------------------------------
What:   src/lib.rs, ModuleWithRelocations::build_code_call_graph - a
        relocation of type R_WASM_TYPE_INDEX_LEB is skipped. Every other
        relocation type in the code section names a symbol; this one carries
        a TYPE index (the signature immediate of a `call_indirect`), and
        upstream looked that number up as if it were a symbol index. The same
        skip is part of upstream's pull request DioxusLabs/dioxus#5915, which
        was closed unmerged.
Why:    the lookup linked a function to whatever symbol happens to have the
        number of the type it calls through - in the reproduction, a closure
        `invoke` shim to the split export of route Two. Those edges are
        false. Before 0001 they only made the splitter's sets larger; with
        0001 the recovered shims carry them into the main module's graph, and
        through them most of every split route's code.
Effect: the call graph no longer has those false edges. Removing edges that
        are not references cannot make anything that is used look unused, so
        this does not weaken 0001. With both patches the reproduction builds,
        the functions only the split route uses leave the main module again,
        and a split route's piece holds that route's code.
Drop when: with 0001, when upstream fixes the type-index lookup.


0003-deterministic-split-module-sections.patch
----------------------------------------------
What:   src/lib.rs, two places where the splitter writes a split module:
        - create_ifunc_initializers collects the function-table entries a
          split module fills in a BTreeMap keyed by table offset instead of a
          HashMap, so it adds its element segments in offset order;
        - clear_data_segments takes the module's data symbols in sorted order
          (by symbol number) instead of in the iteration order of a HashSet
          when it adds one data segment per symbol.
        Nothing else: what is emitted is the same, only its order is fixed.
        Upstream has exactly this change as an open pull request,
        DioxusLabs/dioxus#5992 ("wasm-split: emit split modules
        deterministically", a BTreeMap by table offset and the data segments
        in Node order), and an open issue, #6090 ("dx build --wasm-split gives
        different split modules (and hashed names) for identical input")
        (both checked 2026-11-19; neither merged nor closed).
Why:    Rust's HashMap and HashSet are seeded at random in every process, so
        their iteration order differs from one run of dx to the next. Walrus
        writes element and data segments in the order they were added, so two
        builds of the SAME source gave every split module (module_*.wasm)
        different bytes - the same sections, the same sizes, the element and
        data sections in another order - and with them other content hashes in
        their file names, another __wasm_split.js (which lists those names)
        and another glue .js (which carries a hash of the loader). An
        application whose source did not change was renamed on every build,
        and every visitor's browser downloaded all of it again. Measured on
        the ApplicationSplitter sample's sales application: rustc's .wasm, the
        main module and chunk_0 were identical across two clean builds; all
        ten module_*.wasm differed only in their data section (and, in the
        larger ones, their element section). The standalone splitter run
        three times on the same two input files gave three different sets of
        split modules; with this patch, three identical ones.
Effect: a split build is a pure function of its input: the same source gives
        the same split modules, the same names, the same loader and the same
        glue file. Sizes do not change (the same segments, in a fixed order).
        Unsplit builds do not run the splitter and are unaffected.
        NOT changed: SplitModule::relies_on_chunks stays a HashSet. dx lists
        a split module's chunks in the loader in that set's order, but the
        splitter always makes exactly one chunk (build_split_chunks pushes one
        set), so the set holds at most one number and its order cannot vary.
        If upstream ever makes more than one chunk, that list must be sorted
        too.
Drop when: upstream merges #5992 or an equivalent fix and the repository
        takes a stable release that has it.


0004-keep-main-data-inside-split-symbols.patch
----------------------------------------------
The bug: in a split build, text formatting in the MAIN module could give an
empty text. In the application that reported it, `format!("{}{}", a, b)`
gave "" - and the platform's REST client builds every address with that
expression, so no call left the browser ("Could not reach the server") and
the pages stayed without content. The same code built without splitting
worked.

How it happens, proved on the ApplicationSplitter sample's sales application
by reading the bytes of the linked module and of the split main module:

  - rustc stores each `format!` as a short byte template ending in 00:
    `"{}{}"` is C0 C0 00. A template that starts with 00 formats to nothing.
  - Data symbols can OVERLAP. rustc asks wasm-ld for -O2 at opt-level 2, 3, s
    and z, and at that level the linker stores a constant that is the tail of
    a longer constant inside the longer one. In the sample, the main
    module's C0 C0 00 was the last three bytes of a split page's template
    `"order-{}{}"` (06 "order-" C0 C0 00): two symbols, one of them inside
    the other.
  - prune_main_symbols writes zeros over the whole range of every data symbol
    that only split modules reach (so that wasm-opt can drop the data from
    the main file; the split module writes its symbols back, as active data
    segments, when it is loaded). It did not look at whether a symbol the
    main module keeps lies in that range. The page's template was zeroed and
    the main module's template with it: 00 00 00.
  - The bytes come back when the module that owns the longer constant is
    loaded, so the failure depends on which pages a visitor has opened.

Whether an application is hit depends on which constants it has and which
module owns the longer one, so it comes and goes with unrelated changes. The
sample had one such pair before its diagnostics page existed (the template
of `"{} {}"` inside a page's class text); nothing in its main module used
it.

What:   src/lib.rs, prune_main_symbols - before zeroing, the bytes of the
        first data segment that a KEPT data symbol covers are marked (a kept
        symbol is one that is not in the set of symbols only split modules
        reach); the zeroing loop leaves marked bytes as they are. Nothing
        else changes: a split module still writes back the whole range of
        each of its symbols when it is loaded, which gives the kept bytes
        the value they already have.
Why:    the main module must keep every byte it reads.
Effect: the main module's constants are whole in every split build. The
        main file keeps the few bytes that are both in a kept symbol and in
        a split one (in the sample: 12 bytes, three templates; its sales
        application's files grew by 16 bytes in all). The change does not
        touch what a split module holds. Unsplit builds do not run the
        splitter and are unaffected.
Upstream (checked 2026-11-23): the same defect is upstream's open issue
        DioxusLabs/dioxus#5769 ("wasm-split-cli truncates a live data symbol
        that overlaps a pruned dead one"), with the open pull request #5772,
        which makes the same change (it marks the live bytes and skips them);
        not merged. This patch was written here, before that pull request
        was found; the comments are our own.
How it is checked: the ApplicationSplitter sample's sales application has a
        formatting self-check in its main module and a diagnostics page with
        templates that end like the main module's (the sample's maintainer
        file, CHECKING IN A BROWSER). With upstream's code the self-check
        fails at start and the sample's REST calls fail; with this patch
        both work.
Drop when: upstream merges #5772 or an equivalent fix and the repository
        takes a stable release that has it.


UPGRADING
---------
When dx is upgraded, the crate's version changes with it (dx asks for the same
release of wasm-split-cli). Take the new release's .crate from crates.io (or
the local cargo cache) and record its checksum, check upstream for #5795,
the type-index fix, #5992 and #5772 first, re-apply the patches that are still needed, and
change the [patch] path and version in dx's Cargo.toml (dioxus-cli patch
0007) to match. Then rebuild and check a split build with a field only on a
split page, as above, and build a split application twice from clean: every
file name and every byte must be the same (0003); and open the sample's
sales application: its formatting self-check must pass (0004).
