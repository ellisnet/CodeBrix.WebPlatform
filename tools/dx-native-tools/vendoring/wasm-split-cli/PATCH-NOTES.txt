================================================================================
PATCH NOTES: wasm-split-cli (the WebAssembly bundle splitter inside `dx`)
================================================================================

tools/dx-native-tools/sources/wasm-split-cli is the wasm-split-cli crate exactly
as published on crates.io (the archive beside this file, whose checksum is in
the .sha256 file) with the numbered patches in this folder applied in order.
Nothing else may differ: `LibraryChecker patches` rebuilds the source from the
archive and the patches and compares it with that folder byte for byte.

wasm-split-cli is a library crate of the Dioxus project
(https://github.com/DioxusLabs/dioxus, packages/wasm-split/wasm-split-cli),
"MIT OR Apache-2.0", used under Apache-2.0 like dx itself. It is not a separate
program here: dx links it and runs it for `dx build --wasm-split`. dx's
Cargo.toml substitutes this patched copy for the crates.io crate
(tools/dx-native-tools/vendoring/dioxus-cli, patch 0007), so `cargo vendor`
does not take the crates.io copy and it is not in sources/vendor; the archive
here is the pristine crate.

Each changed place in the source carries a comment that starts "CodeBrix
change:" and points at this file.

THE BUG 0001 AND 0002 FIX
-------------------------
`dx build --platform web --release --wasm-split` panicked right after "Emitting
main bundle split module":

    assertion failed: !self.dead.contains(&id)
    (walrus-0.23.3/src/module/functions/mod.rs, from walrus::passes::gc::run
    in Splitter::emit_main_module)

A small application reproduces it deterministically: two split routes, and an
input field whose handler reads the field's value (`oninput: move |e|
typed.set(e.value())`) on ONE of them and nowhere in the main module. Upstream
issue DioxusLabs/dioxus#4769 reports the same panic (open).

How the splitter works: it builds a call graph of the program from the
relocations rustc leaves in the module (`--emit-relocs`), pairs the original
module's functions with the module wasm-bindgen wrote, computes what the main
module reaches and what each split route reaches, and deletes from the main
module every function that only split routes reach.

What went wrong, proved by dumping the splitter's sets for that application:

  - wasm-bindgen replaces its "describe" functions with generated glue. A
    describe function is the only code that names the `invoke` shim of a
    closure type (the function JavaScript calls through the function table
    when it calls a Rust closure). The splitter knows this: build_call_graph
    collects everything those vanished functions referenced ("recovered
    children") and every function only wasm-bindgen made, and attaches them
    to `main`. But it attached them in a LOCAL map, `new_call_graph`, that is
    never read again. So those shims were reachable from nothing.
  - They stay in the main module anyway: they sit in the function table,
    which is exported. Two of them (the shims of the closure types js-sys's
    Array::flatMap takes) call alloc::vec::Vec<JsValue>::into_boxed_slice.
    The form code of the split route also calls that function, and nothing
    else in the graph does, so it counted as "only a split route reaches it"
    and was deleted from the main module while the shims still called it.
    walrus's garbage collector then walked the dangling call and panicked.
  - With a field in the main module too (the workaround the
    ApplicationSplitter sample used), the main module itself reaches the
    form code, so nothing the shims call is deleted. Whether a build panics
    therefore depended on which functions a split route happens to share
    with such a shim.

Upstream status (checked 2026-11-19): the code is unchanged on upstream's main
branch, and there is no release after 0.7.10 except 0.8.0 pre-releases, which
this repository does not take. No fix is merged.


0001-recovered-edges-into-call-graph.patch
------------------------------------------
What:   src/lib.rs, build_call_graph - the edges from `main` to the recovered
        children and to the functions only wasm-bindgen made are written into
        `self.call_graph`, the graph the main module's reachability is
        computed from, instead of into the discarded local map
        `new_call_graph`, which is removed (with the empty entries it was
        given). This is exactly the change of upstream's open pull request
        DioxusLabs/dioxus#5795 (its one commit,
        3f6e5a950dfd29cb60ae2d1b76d22c0bd7cd1301), with our own comments.
Why:    it makes the splitter do what its own comments say it does. Without
        it, a function reached only through such a shim can be deleted from
        the main module while still called, and the build panics (above).
Effect: the closure shims, the functions only wasm-bindgen made, and what
        they call are kept in the main module, which they never left; a split
        module that uses one of those functions now imports it from the main
        module instead of deleting it there. The panic is gone. ON ITS OWN
        this patch pins far too much into the main module, because of the
        defect 0002 fixes: in the small reproduction no function at all was
        left in the split routes.
Drop when: upstream merges #5795 or an equivalent fix and the repository
        takes a stable release that has it.


0002-no-edges-from-type-index-relocations.patch
-----------------------------------------------
What:   src/lib.rs, ModuleWithRelocations::build_code_call_graph - a
        relocation of type R_WASM_TYPE_INDEX_LEB is skipped. Every other
        relocation type in the code section names a symbol; this one carries
        a TYPE index (the signature immediate of a `call_indirect`), and
        upstream looked that number up as if it were a symbol index. The same
        skip is part of upstream's pull request DioxusLabs/dioxus#5915, which
        was closed unmerged.
Why:    the lookup linked a function to whatever symbol happens to have the
        number of the type it calls through - in the reproduction, a closure
        `invoke` shim to the split export of route Two. Those edges are
        false. Before 0001 they only made the splitter's sets larger; with
        0001 the recovered shims carry them into the main module's graph, and
        through them most of every split route's code.
Effect: the call graph no longer has those false edges. Removing edges that
        are not references cannot make anything that is used look unused, so
        this does not weaken 0001. With both patches the reproduction builds,
        the functions only the split route uses leave the main module again,
        and a split route's piece holds that route's code.
Drop when: with 0001, when upstream fixes the type-index lookup.


0003-deterministic-split-module-sections.patch
----------------------------------------------
What:   src/lib.rs, two places where the splitter writes a split module:
        - create_ifunc_initializers collects the function-table entries a
          split module fills in a BTreeMap keyed by table offset instead of a
          HashMap, so it adds its element segments in offset order;
        - clear_data_segments takes the module's data symbols in sorted order
          (by symbol number) instead of in the iteration order of a HashSet
          when it adds one data segment per symbol.
        Nothing else: what is emitted is the same, only its order is fixed.
        Upstream has exactly this change as an open pull request,
        DioxusLabs/dioxus#5992 ("wasm-split: emit split modules
        deterministically", a BTreeMap by table offset and the data segments
        in Node order), and an open issue, #6090 ("dx build --wasm-split gives
        different split modules (and hashed names) for identical input")
        (both checked 2026-11-19; neither merged nor closed).
Why:    Rust's HashMap and HashSet are seeded at random in every process, so
        their iteration order differs from one run of dx to the next. Walrus
        writes element and data segments in the order they were added, so two
        builds of the SAME source gave every split module (module_*.wasm)
        different bytes - the same sections, the same sizes, the element and
        data sections in another order - and with them other content hashes in
        their file names, another __wasm_split.js (which lists those names)
        and another glue .js (which carries a hash of the loader). An
        application whose source did not change was renamed on every build,
        and every visitor's browser downloaded all of it again. Measured on
        the ApplicationSplitter sample's sales application: rustc's .wasm, the
        main module and chunk_0_split were identical across two clean builds; all
        ten module_*.wasm differed only in their data section (and, in the
        larger ones, their element section). The standalone splitter run
        three times on the same two input files gave three different sets of
        split modules; with this patch, three identical ones.
Effect: a split build is a pure function of its input: the same source gives
        the same split modules, the same names, the same loader and the same
        glue file. Sizes do not change (the same segments, in a fixed order).
        Unsplit builds do not run the splitter and are unaffected.
        NOT changed: SplitModule::relies_on_chunks stays a HashSet. dx lists
        a split module's chunks in the loader in that set's order, but the
        splitter always makes exactly one chunk (build_split_chunks pushes one
        set), so the set holds at most one number and its order cannot vary.
        If upstream ever makes more than one chunk, that list must be sorted
        too. (Patch 0007, which can make several, makes it a BTreeSet.)
Drop when: upstream merges #5992 or an equivalent fix and the repository
        takes a stable release that has it.


0004-keep-main-data-inside-split-symbols.patch
----------------------------------------------
The bug: in a split build, text formatting in the MAIN module could give an
empty text. In the application that reported it, `format!("{}{}", a, b)`
gave "" - and the platform's REST client builds every address with that
expression, so no call left the browser ("Could not reach the server") and
the pages stayed without content. The same code built without splitting
worked.

How it happens, proved on the ApplicationSplitter sample's sales application
by reading the bytes of the linked module and of the split main module:

  - rustc stores each `format!` as a short byte template ending in 00:
    `"{}{}"` is C0 C0 00. A template that starts with 00 formats to nothing.
  - Data symbols can OVERLAP. rustc asks wasm-ld for -O2 at opt-level 2, 3, s
    and z, and at that level the linker stores a constant that is the tail of
    a longer constant inside the longer one. In the sample, the main
    module's C0 C0 00 was the last three bytes of a split page's template
    `"order-{}{}"` (06 "order-" C0 C0 00): two symbols, one of them inside
    the other.
  - prune_main_symbols writes zeros over the whole range of every data symbol
    that only split modules reach (so that wasm-opt can drop the data from
    the main file; the split module writes its symbols back, as active data
    segments, when it is loaded). It did not look at whether a symbol the
    main module keeps lies in that range. The page's template was zeroed and
    the main module's template with it: 00 00 00.
  - The bytes come back when the module that owns the longer constant is
    loaded, so the failure depends on which pages a visitor has opened.

Whether an application is hit depends on which constants it has and which
module owns the longer one, so it comes and goes with unrelated changes. The
sample had one such pair before its diagnostics page existed (the template
of `"{} {}"` inside a page's class text); nothing in its main module used
it.

What:   src/lib.rs, prune_main_symbols - before zeroing, the bytes of the
        first data segment that a KEPT data symbol covers are marked (a kept
        symbol is one that is not in the set of symbols only split modules
        reach); the zeroing loop leaves marked bytes as they are. Nothing
        else changes: a split module still writes back the whole range of
        each of its symbols when it is loaded, which gives the kept bytes
        the value they already have.
Why:    the main module must keep every byte it reads.
Effect: the main module's constants are whole in every split build. The
        main file keeps the few bytes that are both in a kept symbol and in
        a split one (in the sample: 12 bytes, three templates; its sales
        application's files grew by 16 bytes in all). The change does not
        touch what a split module holds. Unsplit builds do not run the
        splitter and are unaffected.
Upstream (checked 2026-11-23): the same defect is upstream's open issue
        DioxusLabs/dioxus#5769 ("wasm-split-cli truncates a live data symbol
        that overlaps a pruned dead one"), with the open pull request #5772,
        which makes the same change (it marks the live bytes and skips them);
        not merged. This patch was written here, before that pull request
        was found; the comments are our own.
How it is checked: the ApplicationSplitter sample's sales application has a
        formatting self-check in its main module and a diagnostics page with
        templates that end like the main module's (the sample's maintainer
        file, CHECKING IN A BROWSER). With upstream's code the self-check
        fails at start and the sample's REST calls fail; with this patch
        both work.
Drop when: upstream merges #5772 or an equivalent fix and the repository
        takes a stable release that has it.

0005-skip-data-symbols-without-bytes.patch
-------------------------------------------
The bug: a split build failed inside dx, after "Emitting main bundle split
module", with

    Failed to emit wasm split modules
    Caused by: Failed to find data symbol

and wrote nothing. It was seen in a split DEBUG build of another application;
the ApplicationSplitter sample built fine in debug and release.

How it happens, proved on a scratch copy of the sample's sales application:

  - The splitter's call graph takes its data nodes from the relocations of
    the linked module: every relocation that names a DATA symbol gives a
    node, whatever the symbol's size (get_symbol_dep_node).
  - Its table of data symbols (parse_bytes_to_data_segment) leaves out the
    symbols of size 0 (and has no undefined ones), because they have no
    bytes.
  - prune_main_symbols looks up every data node that only split modules
    reach, to zero its bytes in the main module, and failed the build when a
    node was not in the table. A data symbol of size 0 that only a split
    module names is exactly that: a zero-sized static, such as
    tracing_core's NO_SUBSCRIBER, used only by code in a piece.
  - The sample has three such symbols in its debug build (__heap_base,
    __heap_end and NO_SUBSCRIBER), all named from the main module too, so it
    was not hit. Adding one zero-sized static named only by its diagnostics
    page (`static SPLIT_ONLY_MARKER: Marker = Marker;`, its address shown on
    the page) gave exactly the error above in a split debug build.
  - clear_data_segments, which writes a split module's own data, already
    skips a symbol that is not in the table.

What:   src/lib.rs, prune_main_symbols - a data node that is not in the table
        is skipped instead of failing the build. Nothing else.
Why:    such a symbol has no bytes in the main module, so there is nothing to
        zero; the other place that uses the table already treats it so.
Effect: the build no longer fails there; the output is otherwise unchanged
        (nothing was zeroed for such a symbol before either - the build
        stopped). With the reproduction, the split debug build succeeds and
        the page (its zero-sized static's address included), the sample's
        formatting self-check and every piece work in headless Chrome.
Upstream (checked 2026-11-24): the lookup is unchanged on upstream's main
        branch (packages/wasm-split/wasm-split-cli/src/lib.rs); the issue
        tracker was not searched.
How it is checked: the reproduction above (a scratch copy only; the sample
        itself is unchanged): with the patch, a split debug build of it
        succeeds; without it, it fails with the message above.
Drop when: upstream skips (or records) data symbols without bytes and the
        repository takes a stable release that has it.


0006-shared-code-into-the-chunk.patch
-------------------------------------
The defect: in every split build the one shared chunk (chunk_0_split) was
empty (283 bytes), and the code and data that several split modules use were
written into EACH of them. Measured on a scratch copy of the
ApplicationSplitter sample's sales application (eleven split modules), release:
108 function-table slots were filled by two to eight modules each, every one
with its own copy of the function, and 140,727 data addresses were written by
more than one module.

How it happens:

  - build_split_chunks is meant to put every symbol that more than one split
    module reaches, and the main module does not hold, into one chunk. The
    loop that should record which modules reach a symbol had NO BODY after
    its `continue`, so the table stayed empty and so did the chunk.
  - The rest of the path was unfinished too, which the empty table hid:
    - emit_split_chunk imported nothing and deleted every function of the
      main module from the chunk, also the ones the chunk's functions call:
      with the loop filled in, walrus panicked at once ("assertion failed:
      !self.dead.contains(&id)");
    - the functions of a chunk had no slots in the function table, so a
      split module had no way to call them: emit_split_module took them off
      the module's own list (so the module no longer filled their original
      table slots or wrote their data) but left their code in the module;
    - the loader (__wasm_split.js) marked a file as loaded only after it had
      been instantiated, so every module that asked for the chunk while it
      was still loading fetched and instantiated it again (measured with
      upstream's loader: four calls at once for two modules with one chunk
      fetched the chunk four times), and a module was instantiated even when
      a chunk it needs had failed to load, with the chunk's functions and
      data missing.

What:   src/lib.rs
        - build_split_chunks records, for each symbol the main module does
          not hold, the split modules that reach it (the missing line). A
          split point's own entry function is left out: its module exports
          it and puts it into the function table itself.
        - The function table gets one more slot for each function of the
          chunk, after upstream's added slots (one per split point, one per
          symbol the split modules share with the main module). One number
          (ifunc_table_growth) and one order of the chunk's functions
          (chunk_functions: the order of their ids in the source module)
          serve the main module, the chunk and every split module, so that
          all of them declare the same table and agree on every slot. The
          main module leaves the new slots empty.
        - emit_split_chunk treats the chunk like a split module: what the
          chunk's symbols reach in the main module becomes calls through the
          table (as in a split module), the rest of the main module's
          functions are deleted; and it adds one element segment that puts
          the chunk's functions into their slots. (It fills the functions'
          ORIGINAL table slots - the "holes" of the main module - and writes
          the chunk's data symbols back as before, through the functions a
          split module uses for its own.)
        - emit_split_module (add_split_imports) turns each chunk function
          the module uses into a call through the chunk's slot, so the
          module no longer carries the code.
        - For an EMPTY chunk every one of these is what it was: no slot, no
          segment, the same sets.
        src/__wasm_split.js (makeLoad)
        - a file is fetched and instantiated once, also when it is asked for
          again while it is loading (every caller waits for the one load and
          then gets its own callback, as before);
        - the returned function answers true when the file is loaded and
          false when it is not, and a module whose chunk did not load is
          not fetched or instantiated: it fails the way it fails when its
          own file does not load (the error on the console, no callback).
Why:    a visitor downloaded the same code once per page, and code that
        every page needs made every page's piece large. The loader change
        belongs to it: a chunk is asked for by every module that needs it,
        it must be there before any of them runs, and it should be
        downloaded once.
Effect: - The chunk file holds the shared code and data once; each module
          that uses any of it names the chunk as its dependency in the
          loader (the list dx writes, `makeLoad(url, [__wasm_split_load_
          chunk_0], ...)`, was already there and is now real), and the
          browser fetches the chunk once, before the first such module.
        - Measured (the scratch copy above, which also has one substantial
          function used by two pages and one hand-split piece only; release,
          raw / Brotli bytes): all pieces together 662,508 / 263,248 before,
          388,317 / 151,131 after (chunk 107,977 / 46,932); the Orders page
          138,614 / 56,432 -> 50,838 / 17,118, the Reports page 82,258 /
          38,335 -> 27,409 / 10,534, the forecast piece 42,818 / 23,776 ->
          6,795 / 3,471. Opening Orders and then Reports downloaded 94,767
          Brotli bytes of pieces before and 74,584 after.
        - THE COST: there is ONE chunk, so the FIRST page a visitor opens
          also brings everything any two modules share. In the same build a
          first visit to the Overview page alone went from 33,781 to 58,182
          Brotli bytes of pieces (11,250 + the chunk). An application should
          keep large code that only some pages need behind ONE lazily loaded
          piece of its own, so that it is not "shared" and stays out of the
          chunk. (One chunk per group of users is not an answer here: the
          sample's 220 shared functions have 74 different sets of users.)
        - The main module: its code and data are unchanged; only the size of
          its function table grows (by the number of chunk functions).
        - Calls into the chunk go through the function table, like the calls
          from a split module into the main module.
        - An application without split points and every unsplit build are
          byte for byte what they were. A split application whose modules
          share nothing outside the main module keeps every .wasm file byte
          for byte; its loader file has the new makeLoad, so that file, the
          main script (which carries a hash of the loader) and index.html
          change once, with their names.
        - The output stays a pure function of the input (0003): the chunk's
          functions are taken in a fixed order, and its segments are written
          by the functions 0003 already made deterministic.
        - 0004 holds unchanged: the chunk's symbols were already in the set
          the main module zeroes around its kept bytes; the chunk writes
          back the whole range of each of its symbols, as a split module
          does.
        NOT changed: there is still exactly one chunk, and
        SplitModule::relies_on_chunks stays a HashSet (see 0003: with one
        chunk its order cannot vary). (Patch 0007 makes several chunks
        possible, on request, and orders that set.) A failed load still never calls the
        Rust side back (upstream's behaviour; the page keeps waiting).
Upstream (checked 2026-11-24): the empty loop is unchanged on upstream's main
        branch. There is an OPEN, unmerged pull request, DioxusLabs/dioxus
        #5738 ("fix(wasm-split): deduplicate shared residual symbols", head
        0a66368). It was read and NOT ported, for these reasons, each from
        its diff (it was not run here): it makes one chunk per exact set of
        users and numbers the chunks in the iteration order of a HashMap, so
        the output would differ from run to run (0003); it keeps the chunks'
        functions in the main module as well (they are taken out of
        unused_main_symbols and put into the main module's own table
        segment), so the shared code would be downloaded with the main
        module AND with the chunk; it changes unrelated things (it removes
        the export of the non-funcref tables, reorders the main module's
        steps, rewrites the element segments as expressions); and its
        chunk-to-chunk dependencies are written only by the crate's test
        harness, not by dx. Two things in this patch are the same idea as
        in that pull request, written here: recording the users in
        build_split_chunks, and loading a file once in the loader. Another
        open pull request, #6042 ("settle the loader when a chunk fails to
        load"), changes the wasm-split runtime crate as well, which this
        repository uses unpatched; not taken.
How it is checked: on a scratch copy of the ApplicationSplitter sample with
        the shared function described above, with dx built from this source
        and from the source before this patch:
        - a split release build from clean, then again without cleaning, and
          a split debug build twice: every file name and every byte the same;
        - every .wasm file of the split site read back and checked: all
          pieces import the table with the main module's limits; no table
          slot is filled by two files; every call through a constant table
          index (the stubs: module -> chunk, module -> main, chunk -> main,
          main -> module) goes to a slot that exactly one file fills with a
          function of the same signature; no two pieces write the same
          address; the main module's data is byte for byte that of the
          build before the patch; every data byte and every table slot a
          module wrote before the patch is written by that module or by the
          chunk;
        - in headless Chrome, release and debug: every page as a deep link,
          every ordered pair of pages, the three lazy forms, one session
          through all pages both ways; the formatting self-check (0004) and
          the diagnostics page at 0, the REST calls answered, no console
          error; the chunk requested once per page load; the shared
          function giving the same results from both pages and the piece;
          and the loader called four times at once for two modules with
          one chunk (one fetch each), and with a chunk that does not exist
          (the module answers false and is not fetched);
        - a dx with the recording line of build_split_chunks switched off
          (so the chunk stays empty) and everything else of this patch in
          place: all thirteen .wasm files of the split site byte-identical
          to the build before the patch;
        - the sample's two applications without split points, the sales
          application built WITHOUT splitting (release and debug), and the
          WorkSite frontend: byte-identical to the build with the source
          before this patch; `dx serve` of the sales application works as
          before.
Drop when: upstream fills the shared chunk itself (its own fix of the empty
        loop, #5738 or another) with a loader that loads a chunk once, and
        the repository takes a stable release that has it. Before dropping,
        check the three points above against upstream's version: the same
        output on every run, the shared code NOT also in the main module,
        and dx writing every chunk dependency.

0007-several-shared-chunks.patch
--------------------------------
The cost 0006 left: there is ONE shared chunk, and every split module that
uses any shared code depends on it, so the first page a visitor opens brings
everything any two split modules share - also code that only lazily loaded
parts use. Measured on an application with one engine piece used by eight
film pieces and a few route pieces (release, Brotli, pieces only; the main
module is the same in every case): its first page fetched 453 KB of pieces
(its own 11 KB and the chunk's 442 KB), of which nearly all was the engine's
and the films' shared code.

What:   src/lib.rs only.
        - SplitOptions (new, public): chunk_threshold (Option<usize>, bytes)
          and chunk_limit (usize, DEFAULT_CHUNK_LIMIT 16). Default: no
          threshold - ONE chunk, exactly 0006's output.
          Splitter::new_with_options (new, public) takes them;
          Splitter::new is new_with_options with the default, so its output
          is byte for byte what it was. A threshold or a limit of 0 is
          refused (an error, before anything is read).
        - build_split_chunks records the users in ordered maps and hands the
          grouping to assign_shared_chunks (new): with no threshold, one chunk
          with every shared symbol (0006). With one:
            users(s)  = the split modules (by index) that reach symbol s,
                        for every s that two or more reach and the main
                        module does not hold (0006's set);
            groups    = the symbols grouped by their EXACT set of users;
            size(G)   = the bytes of G before optimisation: each function's
                        body in the module wasm-bindgen wrote (walrus
                        original_range) plus each data symbol's size
                        (node_size, new); imported functions count 0;
            large     = the groups with size >= threshold, largest first
                        (ties: the user set), at most chunk_limit - 1 of
                        them, then sorted by user set;
            chunk 0   = the common chunk; chunk i + 1 = large[i];
            each other group goes to the large group with the FEWEST users
            among those whose users include all of its own (ties: the
            smaller group, then the user set) - else to chunk 0.
          A limit of 1 therefore also gives the one chunk of the default.
        - emit_split_chunk imports what the chunk reaches in the main module
          OR IN ANOTHER CHUNK. With only the main module's symbols, a chunk
          kept a private copy of every function of another chunk it calls
          (measured: 862 functions copied, one chunk 784 KB instead of 312
          KB); now those calls go through the other chunk's table slots
          (convert_chunk_funcs_to_imports, from 0006, already handled them).
        - SplitModule::relies_on_chunks is a BTreeSet (it was a HashSet,
          see 0003), so dx lists a module's chunks in one fixed order.
        - accumulate_split_points splits a split point's import name at
          "___00_import_" instead of the first "___00": a module name
          holding "___00" (extern "a___00b") was cut short and the build
          panicked ("Could not find export"). Names without "___00" are read
          as before.
        - Unit tests of the grouping (mod shared_chunk_tests, `cargo test
          --lib`): no threshold, nothing shared, a group at the threshold,
          the superset rule and its ties, the common chunk, the limit, and
          that every symbol lands in exactly one chunk.
        Nothing else: the table layout of 0006 (one slot per chunk function,
        chunk after chunk, in the order of chunk_functions) serves several
        chunks unchanged; the loader (src/__wasm_split.js) is unchanged.
Why:    with a threshold, code that only some split modules share is fetched
        only by them. A small group joins a LARGER group all of whose users
        are its users too, rather than the common chunk: that adds no new
        downloader to any chunk (every split module that uses the small
        group already fetches the larger one), where the common chunk makes
        every page that needs any common code download it too.
Effect: - No threshold (every caller of Splitter::new, and dx without its
          variable): byte for byte as before - checked on three applications
          (every .wasm and the loader).
        - A threshold: chunks 1 and up hold the large groups, chunk 0 the
          rest. The main module is byte for byte the same at every threshold
          (the number of chunk functions, and so its table, is the same).
          When no group reaches the threshold the output is exactly the one
          chunk of before.
        - Measured on scratch copies (release, wasm-opt as dx runs it, Brotli
          quality 11, pieces only; "first visit" = a piece and its chunks):
            engine + films application, 12 split modules, 164 user sets
            (1.41 MB of shared code before optimisation):
              one chunk     first route 453 KB, film route 473, not-found
                            442, a film 463 to 834, engine 661
              16 KiB        9 chunks: first route 62, film route 82,
                            not-found 6, films 99 to 823, engine 636
              32 KiB        6 chunks: first route 60, film route 80
              64 KiB        4 chunks: first route 91, film route 111
            the ApplicationSplitter sample's sales application, 11 split
            modules, 68 user sets (62 KB shared):
              one chunk     pages 25 to 40 KB
              16 KiB        2 chunks: three pages 2.2 KB larger (36.8 ->
                            39.0, 40.2 -> 42.4, 38.4 -> 40.6), the other eight
                            10 to 11 KB smaller (34.8 -> 24.0, 25.8 -> 15.0)
              32 KiB        no group large enough: byte for byte as before
            a site with 19 split modules, 63 user sets (151 KB shared):
              16 KiB        3 chunks: every page 5 to 6 KB smaller, two
                            larger pieces 22 KB smaller
              32 KiB        2 chunks: most route pages about 2 KB larger,
                            the two larger pieces 22 KB smaller
          Downloading every piece costs 0.4 to 1.8 per cent more at 16 KiB
          (more files, less shared compression). An extra chunk costs about
          0.8 to 2.2 KB. Before optimisation the bytes are about the size of
          the optimised file, and its Brotli copy about a third of that.
          Merging a small group into the common chunk instead of into a
          larger group of its users (measured, 32 KiB, the engine + films
          application): first route 145 KB instead of 60, film route 165
          instead of 80.
        - A split module lists every chunk it uses; chunks list none (dx
          writes them `makeLoad(url, [], ...)`, as before). Why that is
          enough: see THE INVARIANT below.
THE INVARIANT (why chunks need no dependency lists of their own): a split
        module m depends on chunk Y when m REACHES a symbol of Y in the call
        graph (emit_split_module). Reachability is transitive, through calls
        and through data relocations (a vtable or a function pointer stored
        in data is an edge too). So whoever can reach a symbol x of chunk X
        that uses a symbol y of chunk Y reaches y as well, is itself a user
        of y, and lists Y. Code of X runs only when a split module calls it,
        and that module has listed and loaded Y first. A module that loads
        X only for OTHER symbols of X (a small group placed in X by the
        superset rule) never runs x, so Y not being loaded for it does no
        harm: instantiating X runs no code (a split module or chunk has no
        start function), it only fills X's own table slots and writes X's
        own data, and the stubs in X that call into Y are just constant
        table indices until called. The same holds for data: X's code that
        reads Y's data runs only for modules that reached that data and so
        listed Y. Every symbol is in exactly one chunk, every table slot is
        filled by exactly one file and every data byte is written by one
        file (or, for constants the linker stored inside one another, by
        several with the same bytes), so the order in which chunks are
        instantiated does not matter; the loader fetches a module's chunks
        in parallel and instantiates the module after all of them.
DETERMINISM: every map and set that decides an order is ordered (BTreeMap,
        BTreeSet) and every tie is broken explicitly (size, then user set);
        the split modules' indices come from their sorted import names
        (upstream) and the sizes from the input bytes. The output is a pure
        function of the input and the two options: three runs in separate
        processes gave byte-identical files for each of three applications
        and three thresholds. Nothing depends on the machine.
FAILURE: unchanged loader behaviour - a module whose chunk fails to load is
        not instantiated, the error goes to the console, the chunks that did
        load stay loaded (harmless: their code runs only when a module that
        loaded completely calls it), and a failed chunk is fetched again by
        the next call.
Rejected alternatives:
        - one chunk per exact user set (upstream's open pull request #5738;
          see 0006): 63 to 164 files for the applications above, and that
          pull request numbers its chunks in hash order;
        - clustering the user sets (upstream's comment names Louvain): hard
          to reason about, and a small change to the program would reshuffle
          the chunks;
        - small groups always into the common chunk: measured above, every
          page that uses any common code downloads them;
        - copying small groups into every split module that uses them
          (upstream before 0006): several files would fill one table slot
          and write the same data, and a second module's load would reset a
          mutable static;
        - a threshold in compressed bytes: wasm-opt runs after the splitter,
          so they are not known here.
Open risks:
        - when a group's size crosses the threshold the chunks are numbered
          anew (their names change with their content anyway);
        - a module may depend on up to chunk_limit chunks, fetched in
          parallel: fine over HTTP/2, queued over HTTP/1.1;
        - the three applications above were checked in headless Chrome
          (two of them; every page, the hand-split parts, no console error,
          each chunk fetched once) and statically (the third); split DEBUG
          builds with several chunks were checked by the platform's opt-in
          build test only.
How it is checked: on scratch copies of three applications' split builds
        (rustc's .wasm, wasm-bindgen 0.2.130 as dx runs it, this splitter,
        wasm-opt as dx runs it; the unpatched pipeline reproduced the
        shipped files byte for byte):
        - no threshold, and a limit of 1: every .wasm and the loader byte
          for byte as before;
        - thresholds of 1 KiB to 256 KiB and limits of 4 and 16: read back
          with the static checker (tools/dx-native-tools/split-check): all
          pieces import the main module's table; no table slot is filled by
          two files; every call through a constant table index goes to a
          slot that exactly one file fills with a function of the same
          signature; no module calls into a chunk it does not list; no two
          files write different bytes at one address; against the one-chunk
          build of the same input: the same data bytes written by the pieces
          in all, every hole of the main module filled by the same function,
          the same set of functions, and the main module's data and code the
          same;
        - in headless Chrome (the ApplicationSplitter sample's sales
          application with 1, 2 and 11 chunks; the engine + films
          application with 6 and 9 chunks, through software WebGPU): every
          page as a deep link and in one session both ways, the hand-split
          parts, the sample's formatting self-check at 0, no console error,
          each chunk requested once per page load;
        - three runs of each, byte-identical;
        - `cargo test --lib` (the grouping's unit tests).
Drop when: upstream groups shared code into several chunks deterministically,
        with its chunks importing one another's code, and the repository
        takes a stable release that has it; until then keep it with 0006.
